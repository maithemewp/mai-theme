# Mai Theme v3: a block theme starter built on Mai Slots

Revised 2026-10-23 to match Mike's review of the first build. The first build's own rulings are in the plan's "Decided while building" section. Amended the same day with the calls the review-changes build made (`docs/plans/2026-10-23-mai-theme-v3-review-changes.md`), each marked "agent's call" where it appears.

Brainstormed with Mike and approved on 2026-10-20. This describes what to build and why, and marks every choice that was the agent's call rather than Mike's.

## What it is, and why now

**Mai Theme v3 is the starter every new Mai block theme client site is copied from.** It may later be sold as a premium theme, but for now it is a starting point for BizBudding's own builds. Mai Custom Content Areas and the v2 Genesis themes carry on separately. Nothing migrates onto this.

**It exists because Mai Slots needs templates that already hold Slot blocks.** The engine's smoke test showed that 12 of its 14 locations do nothing until a template has a Slot block for them. A starter that ships them fixes that for every site built from it. There is no Mai block theme starter today. Every theme in `~/Themes` is a classic Genesis child theme, and `~/Themes/mai` ("Mai Theme FSE" 3.0.0) is a leftover client snapshot with broken references.

**It also writes down how Mike builds block themes now.** beof, balloon-juice, and Horizon West Happenings each settled things a little differently. The starter picks one answer for each, and a shared skill records them (see "Conventions").

## Goals

- A client site starts with every Mai Slots location working, with no template editing.
- The code matches Mike's three recent block themes, using the newest choice where they differ.
- A client copy is easy to restyle: colours, fonts, and shadows change in `theme.json` and nothing else breaks.
- Starter fixes reach an older client copy with `composer update`, without touching that client's own code.

## Non-goals

- Migrating anything from v2, Mai CCA, or Genesis.
- A product launch. Premium packaging, style variations for buyers, and a pattern library are a later phase.
- Moving mai-content-areas to GitHub dependencies with committed `vendor/` and `build/`. That is parked deliberately. It has to happen before the theme first goes on a real site, but not in this build.
- Section styles. Parked until the pattern library.

## Anti-goals

- A template that silently loses content, for example a Slot block deleted by a client.
- Token names that promise a look, like `large` for a shadow, or a palette slug whose label says something else, as Ollie's `secondary` labelled "Base Accent" does.
- A framework or helper API. Mike had `mai-builder` once and it was over-engineering. The plumbing package is a handful of plain hooks calling core, with no helpers and no config.
- Anything that raises WordPress's default presets back into the page: core's gradients, duotone filters, shadows, and colours.

## The repo

- **Name:** `mai-theme`. Repo `maithemewp/mai-theme`, folder `~/Themes/mai-theme`, text domain `mai-theme`, version `3.0.0`. The theme's own PHP uses the namespace `Mai\Theme` and the package uses `Mai\Theme\Core` (see "PHP").
- **`mai-theme` names this theme and its package. `mai` names what the theme does.** `mai-theme` stays in the folder, slug, and text domain, the repo, `maithemewp/mai-theme-core` and `Mai\Theme\Core`, and the `mai-theme-scaffold` skill. Everything else drops `-theme`: the stylesheet handle is `mai`, block CSS handles are `mai-<namespace>-<block>` (such as `mai-core-navigation`), hooks start `mai_` (such as the installer filter `mai_dependencies`), CSS variables start `--mai-` (such as `--mai-site-min-height`), and pattern slugs start `mai/` (such as `mai/posts-grid`). Bindings and blocks use `mai/` too, as in `mai/current-year`.
- **Taking over the old repo is safe.** `maithemewp/mai-theme` is the v1 Genesis child theme (1.4.0, built for Mai Theme Engine, last pushed June 2022). It has no updater of its own and no tags on GitHub, so pushing v3 cannot reach any site still running 1.x. Mai Engine only uses `mai-theme` as an admin page slug, on v2 sites that will not run this theme. Neither `mai` nor `mai-theme` is in the WordPress.org theme directory.
- **History:** keep v1's history on a `v1` branch and start `main` fresh at 3.0.0. `~/Themes/mai-theme` is the v1 checkout on `develop`. v3 is built on a local orphan branch `v3`, checked out as a git worktree at `~/Themes/mai-theme-v3`, so the v1 checkout is never touched. Turning `v3` into `main` and moving v1 to a `v1` branch happens when Mike approves the first push. Pushing, tagging, and releasing each need Mike's yes first.
- **Why the slug is not `mai`:** "mai" is already the prefix of what the theme does, from every `wp:mai/slot`, location id like `mai/before-footer`, and `mai/columns` block to the `mai` stylesheet handle. A longer slug keeps the theme's own name apart from them.
- **Repo files:** `AGENTS.md` with `CLAUDE.md` as a symlink to it, `STATE.md`, `TODO.md`, `docs/` in the house shape (`ideas`, `specs`, `plans`, `runbooks`), and a `.distignore` that keeps docs off servers, as balloon-juice has.
- **Floors:** PHP 8.4, because the engine requires it. WordPress 7.0, because the mobile menu uses the navigation overlay part area that 7.0 added.

## How a client site starts

1. Copy the starter folder and name the new folder for the client.
2. Change the theme name, text domain, version, and description in `style.css`, and the package `name` in `composer.json`.
3. Set the client's colours, fonts, and shadows in `theme.json`.
4. Edit templates and parts in code, or in the Site Editor and save back to files with Create Block Theme.

**A client copy is renamed through its folder and `style.css`, never by search and replace.** A search and replace would also rewrite `maithemewp/mai-theme-core` in `composer.json` and the `mai/` names in every template. Nothing else changes name: the package, `Mai\Theme\Core`, the `mai` handles, and `functions.php`'s `Mai\Theme` all stay, and the package never reads the theme's slug (see "PHP").

The README carries this as a numbered procedure, plus the procedure for giving all single posts the sidebar.

## Dependencies

**The theme does not bundle the engine.** Bundling would freeze an engine copy into every client copy, so bug fixes would never reach a site whose plugin is missing. Instead the theme requires Mai Content Areas, which carries the engine and, once it ships with an updater, updates on its own.

**Required plugins are installed through `afragen/wp-dependency-installer`,** the library under v2's `mai-installer`. Read in version 4.3.14:
- **With `optional: false`, it installs and activates the plugin on every wp-admin page load** where the plugin is missing or inactive, so it also re-activates a plugin someone deactivated (`admin_init()`).
- **Installing needs `update_plugins`, activating needs `activate_plugins`.**
- **It removes the plugin's Deactivate and Delete links** (`unset_action_links()`).
- **It downloads a branch, not a release:** `repos/{owner}/{repo}/zipball/{branch}`. Whatever is committed on that branch is what installs.

`mai-installer` itself cannot be reused as it stands: it is hardwired to Mai Engine, adds `mai-engine` theme support, and redirects to Mai Engine's setup wizard.

- **Required:** Mai Content Areas and Mai Columns. Mai Columns builds the header, the footer's columns, the post navigation, both With sidebar templates, and the "Posts: Archive" and "Posts: List" designs, as in beof, and they break without it.
- **Optional:** every other Mai plugin, including Mai Performance Images and Mai Site Help.
- **The dependency config lives in the theme's plumbing package** (see "PHP"), not in a new version of `mai-installer`. A site adds, changes, or removes a required plugin with the `mai_dependencies` filter in its own `inc/` folder.
- **The installer's notices carry the active theme's name.** Left alone, the installer builds the label from a folder slug (`get_dismiss_label()`), so a client copy would show its folder name. `mai-theme-core` returns the "Theme Name" from the active theme's `style.css` through the installer's `wp_dependency_dismiss_label` filter. It runs in wp-admin only, since the notices need `update_plugins`, and reading the name measured 7 microseconds.
- **Blocker for real sites: Mai Content Areas cannot be installed or updated this way yet.** Checked on 2026-10-20: `maithemewp/mai-content-areas` is private, its default branch is `claude/mai-slots-js-editor-home-an9oak`, and it has no updater. A private repo would need a GitHub token in the theme's config, which would then sit in every client copy. Without an updater, "updates on its own" is not true, and that is the whole reason for not bundling the engine. Mai Columns is already in shape: public, `main` branch, and a plugin-update-checker updater (`includes/Updater.php`), at 0.2.0.
- **Decided 2026-10-20: Mai Content Areas ships like Mai Columns before the theme goes on a real site.** Public, `main` as the stable branch, and an updater, folded into the parked shipping work. The installer config names `main`. Making the repo public needs Mike's explicit go-ahead at the time.

**Without Mai Content Areas** (say it was deleted by FTP), Slot blocks render nothing on the front end. Core renders an unregistered block's saved inner content, and a Slot block has none. This was read in `WP_Block::render()`. The Site Editor shows a "doesn't include support" box in each slot's place until the plugin is back. That is a failure someone can diagnose alone, which is the bar.

## Templates

**Standard templates:** `index`, `home`, `front-page`, `page`, `single`, `archive`, `search`, and `404`. Every one follows beof's shape: header part, `<main>` as a constrained group with spacing preset padding (beof's 50 top and 80 bottom), then footer part. `single` is the default for posts and for custom post types.

**Custom templates differ by post type,** set with `postTypes` in `theme.json`'s `customTemplates`:
- **Posts:** the single template, plus With sidebar.
- **Pages:** the page template, plus Wide, Narrow, With sidebar, Blank, and Canvas.

What each custom template is for:
- **Wide:** for hub pages that hold a Query Loop grid.
- **Narrow:** for one-off reading pages.
- **With sidebar:** content plus the sidebar part, built with plain Mai Columns. There are two, one limited to posts and one limited to pages. The posts one carries the meta row, post navigation, and comments, and the pages one carries none of those. They share every part, so only the column wrapper repeats. Agent's call: they are titled "Post with sidebar" and "Page with sidebar", with the slugs `with-sidebar-post` and `with-sidebar-page`, so they can be told apart in the Site Editor's template list. Neither slug starts with `page-` or `single-`, which would collide with WordPress's own template names.
- **Blank:** header and footer, content full width with no padding and no title. For pages built from full-width sections.
- **Canvas:** the content alone, no header or footer.

Wide, Narrow, Blank, and Canvas carry no comments or post navigation, since they are offered on pages only.

There is no "Standard" template. The default template is the standard width, as in Ollie. A custom template cannot become the default, and renaming the default's title to "Standard" through `default_template_types` would also rename "Pages" and "Single Posts" in the Site Editor's template list. Wide, Narrow, and Standard are names v2 users know from Genesis.

**Widths are set natively, with no custom class.** `main`'s Content width sets the template's width: 600px on Narrow, 1200px on Wide, on the four templates that list posts (`index`, `home`, `archive`, and `search`), and on both With sidebar templates, and empty everywhere else, for the 740px default. Agent's call: the With sidebar templates keep `main` at 1200px, as the first build had it, because 740px leaves no room for the sidebar. Their content column measures 836px at a 1440px window, beside the 300px sidebar. Post Content sits directly in each template, full-aligned and constrained with the same Content width, so its blocks follow the template's width and a full-width block in the content still reaches the window edge. Narrow's Post Content also gets a Wide width of 740px, as balloon-juice's Narrow does. Measured as a throwaway on 2026-10-22: `~/tmp/mai-theme-split-compare/`.

**In With sidebar, Post Content is not full-aligned.** It sits in the content column with `{"type":"constrained","contentSize":"100%","wideSize":"100%"}`, as balloon-juice does, so core adds no root padding inside the column.

**The entry is split into a header part and a footer part, with Post Content between them in the template.** That way each template sets its own content width. Posts show a meta row that pages do not, so posts and pages get different header parts rather than one part with a rule (see "Conventions"):
- **`entry-header`:** for single posts and custom post types. Before entry slot, title, a row of date, author, and terms, featured image, and Before entry content slot, inside one wrapper group so they get block spacing.
- **`page-header`:** for pages. The same without the meta row.
- **`entry-footer`:** shared by both. After entry content slot and After entry slot, inside one wrapper group like the headers. Agent's call: without the group, content areas in both slots get no block spacing between them.

`single` and the posts With sidebar use `entry-header`. `page`, Wide, Narrow, and the pages With sidebar use `page-header`. All of them use `entry-footer`.

**Layout patterns for swapping a whole template:** hidden patterns marked `Template Types:` appear as layout choices in the template's Design panel in the Site Editor, whatever the template holds now. The panel matches exact slugs (`pattern.templateTypes?.includes(template.slug)` in core's `editor.js`), so a pattern must list every template it applies to by name. `Inserter: false` does not hide a pattern from that panel. One ships:
- **"Post: With sidebar"**, for Single Posts, built from `entry-header` and `entry-footer`. This is the click version of copying the posts With sidebar template over `templates/single.html`.

**Post designs for the Query Loop replace layout patterns for lists.** Core's "Change design" button on the Query Loop toolbar offers every pattern registered for `core/query` (`PatternPicker` and `getPatternsByBlockTypes` in `block-library.js`, line 64725 in WordPress 7.1.3). The `index`, `home`, `archive`, and `search` templates all share the `posts-grid` part, so switching its Query Loop's design changes every list on the site, and no template's heading is touched. Three designs ship:
- **"Posts: Grid"** (`mai/posts-grid`), the default in `posts-grid`. Three columns of cards: image, title, date, and a short excerpt.
- **"Posts: Archive"** (`mai/posts-archive`). One post per row: a 300px image on the left, and the title, date, and excerpt on the right.
- **"Posts: List"** (`mai/posts-list`). Mai Columns with the left column at 80px, easy to change there, holding a small square thumbnail with the `default` radius, and the title only, vertically centred. For sidebars and "Favorite Posts" sections.

All three use `theme.json` tokens only and include pagination and "Nothing found". "Posts: Grid" and "Posts: Archive" stack on phones. Agent's call: "Posts: List" does not. Mai Columns picks its arrangement from its container's width, not the screen's, and a 300px sidebar counts as a phone-sized container. Stacking would stretch the thumbnail across every sidebar the design is meant for.

Templates stay plain HTML files rather than Ollie's one-line pattern references. Core's pattern block replaces itself with its blocks when a template is opened for editing (`replaceBlocks` in the pattern block's editor code), so a one-line reference does not survive an edit anyway.

**What Create Block Theme 2.10.2 writes back** (read in `theme-templates.php` and `theme-media.php`): the edited template goes to `templates/<slug>.html`. If the template then contains PHP, it is moved into `patterns/<slug>.php` and the template becomes a one-line reference to it. "Localize images" is on by default and inserts PHP for every image (`get_stylesheet_directory_uri()`), so any template with an image comes back as a one-line reference plus a pattern named after the template. The builder documents this in the README, so nobody is surprised to find `patterns/single.php` after a save.

**Layout patterns that contain Slot blocks** must be `Inserter: false`, or limited to templates with `Post Types: wp_template, wp_template_part`. Otherwise WordPress offers them in posts, and inserting one puts a slot in a post. This is in the engine's README.

## Slot blocks in each template

Every location gets a Slot block wherever it applies. An empty Slot block renders nothing, and a missing one leaves an author choosing a location that never shows.

- **Every template except Canvas:** Before header and After header around the header part, Before footer and After footer around the footer part. They sit in the template, outside the parts, so Before header lands outside the `<header>` element.
- **Single, page, Wide, Narrow, and both With sidebar templates:** Before entry and Before entry content inside `entry-header` or `page-header`, and After entry content and After entry inside `entry-footer`.
- **Index, home, archive, and search:** Before entries and After entries, in the template, around the `posts-grid` part.
- **Front page, 404, and Blank:** the four header and footer slots only.
- **Canvas:** none, since it shows only what is on the page.
- **The sidebar part:** Before sidebar content at the top and After sidebar content at the bottom.

"In content" and "In loops" need no Slot block.

**Every starter Slot block is locked against removal, not movement:** `"lock":{"remove":true}`. Deleting a slot silently stops every content area aimed at it. Moving one only makes a database copy of the template. Anyone who can open the Site Editor can unlock a block from its options menu ("Lock movement" and "Lock removal" checkboxes, and `canLockBlocks` defaults to `true` in core).

**Known gap for hub pages:** a Loop insert inside a Query Loop on an ordinary page renders, but the Content Areas "In loops" tab does not list it. The engine's insert store only scans templates, parts, and synced patterns. This belongs in the engine's TODO, not the theme.

## Template parts

- **Header:** a plain `<header>`, the part's default tag. beof wraps its header in a `div` only because its part holds a utility bar above the real header.
- **Mobile menu:** a part in the `navigation-overlay` area with the `navigation-overlay-close` block, as in beof.
- **Footer:** default `<footer>`, in four Mai Columns side by side on desktop and stacked on mobile.
  - **Column 1:** a Site Logo block and a Site Title block, as the header has them, then the Site Tagline in small text and an empty Social Icons block. Agent's call: with no logo set, only the title shows.
  - **Columns 2 to 4:** each a small heading ("Company", "Resources", "Support") and a List block of placeholder links, edited in place.
  - **Bottom row,** in small text: © {year} {Site Title}. The year uses a block binding, `mai/current-year`. `mai/` is the house namespace, as in Mai Locations' `mai/locations` binding, and it survives the rename of a client copy.
- **No footer menu.** A Navigation block with no menu chosen shows the most recently published menu, so a "Footer" menu made later would take over the header. The footer's links are List blocks for that reason.
- **Sidebar:** a `sidebar` part area registered with the `default_wp_template_part_areas` filter, as Horizon West and Ollie do it. The part holds Before sidebar content, a Search block, a Latest posts block, and After sidebar content, so the With sidebar templates look finished before any content area exists. Sidebar content is managed as content areas aimed at the two sidebar slots, so there is no Sidebar item in the admin menu.
- **Entry header, page header, and entry footer:** described under "Templates".
- **Posts grid:** the Query Loop shared by `index`, `home`, `archive`, and `search`, holding the "Posts: Grid" design.

## theme.json

**Copied from what all three themes share:** version 3 with schema 6.9, `appearanceTools` and `useRootPaddingAwareAlignments` on, layout 740px content and 1200px wide, root padding left and right at spacing 40, block gap at spacing 30, and body font size `medium`.

**Values use WordPress's shorthand:** `var:preset|color|primary`, not `var(--wp--preset--color--primary)`. The shorthand is what the editor writes itself. The only raw variables are inside CSS strings, which need them.

**A value is set once, in `theme.json`.** A block in a template, part, or pattern carries a style setting only when it really differs from `theme.json`. The Post Template card gap is the example: it lives in `styles.blocks.core/post-template` and nowhere else, not on the block in `parts/posts-grid.html` and not in `post-template.css`, where it would lose to core's global gap or beat a gap set on the block.

**Core's defaults are removed at the source.** A `wp_theme_json_data_default` filter, the full beof and balloon-juice version, empties core's default palette, gradients, duotone, font sizes, spacing sizes, shadows, and aspect ratios, and sets `spacingScale` steps to 0. Switching defaults off in `theme.json` only hides them from pickers. Horizon West, whose older filter only removes colours, still prints core's shadow and aspect ratio variables on every page, even with `shadow.defaultPresets: false`. beof prints none.

**The filter leaves the image block's aspect ratio control with only "Original"** (read in `AspectRatioTool` in core's `block-editor.js`). Agent's call: the starter adds core's own set back as theme presets, under core's own slugs (`square`, `4-3`, `3-4`, `3-2`, `2-3`, `16-9`, `9-16`), so the control works and the names are ones people already see in core.

**Core's legacy preset classes are stripped too, decided 2026-10-20.** Core's `wp-block-library` common CSS hard-codes seven old gradient classes such as `.has-vivid-green-cyan-to-vivid-cyan-blue-gradient-background`, four old grey colour classes, and four old font size classes (`wp-includes/css/dist/block-library/common.css`). No filter reaches them. But core inlines that file in `wp_maybe_inline_styles()` on `wp_head` at priority 1 and prints it at priority 8, so a `mai-theme-core` hook at priority 2 removes those rules from the inline copy by exact name.
- **Tested 2026-10-20 on mgnv.test** (v2, Mai Engine) with a throwaway must-use plugin, since removed. Core's inline block CSS went from 7,411 to 5,964 bytes. 7 gradient, 4 grey, and 4 font size rules were removed, everything else stayed, and nothing new appeared in `debug.log`.
- **Old content barely uses them.** Of 137,261 published posts across mgnv, balloon-juice, and sportsdataio, none use the gradients or greys, and 2 on mgnv use an old font size.
- **It fails safe.** If core changes those rules, the patterns stop matching and the classes stay. If a page inlines too much CSS, core links the file instead, and the classes stay. If core ever nests rules inside these classes, the patterns would stop at the inner brace and leave a stray `}` that breaks later CSS, so the code keeps core's original text whenever the result's `{` and `}` counts differ. A throwaway check on 2026-10-20 confirmed the guard: a flat rule is removed, a nested one is left untouched.
- **Classes are matched by exact name,** not `*-gradient-background`, so a plugin's own gradient added to the same handle survives.
- **`mai-theme-core` carries a test with no install step,** run against a copy of core's `common.css` and `common.min.css`: all 15 rules removed, `.has-border-color` kept, and braces balanced. Re-run it against each new WordPress release's files.
- **The `:root` variables `--wp--preset--font-size--normal` and `--huge` remain.** They are harmless and nothing in the starter uses them.

**Palette:**
- `base`, `base-2`, `base-3`
- `contrast`, `contrast-2`
- `primary`, `primary-2`

Neutral starter values, agent's call. `primary-2` is the hover colour and the brand's second shade. Global Styles in WordPress 7.1.2 has states for colours: the Button block gets Hover, Focus, Focus-visible, and Active, and the link and button elements also get Link, Any Link, and Visited (read in core's editor code). With custom colours switched off, a hover picked there must come from the palette. `secondary` and the rest are added per client, because adding a colour is always safe and removing one quietly strips it from content that uses it.

**Font sizes:** beof's `x-small` to `xxxx-large`, written as Utopia `clamp()` strings. They render exactly as written (checked on beof's live page). Core's size parser cannot read a `clamp()` string, so it returns the size untouched whether or not a preset has a `fluid` object (`block-supports/typography.php`, the "unsupported units" early return). Agent's call: drop beof's `fluid` min and max objects, which never take effect and only confuse the next reader.

**Spacing:** slugs `10` to `80`. 8px and 16px fixed, then the same Utopia clamps all three themes use.

**Fonts:** Figtree, self-hosted as one variable `woff2` with its OFL licence in `assets/fonts/`, declared through `fontFace` with `fontDisplay: swap`. Two families, both Figtree in the starter:
- **`body`**, shown as "Body: Figtree".
- **`heading`**, shown as "Heading: Figtree".

The slugs are roles, as v2's Mai Engine config names them (`'body' => 'sans-serif:400'`, `'heading' => 'sans-serif:600'`). Swapping a client's heading font is then one file and one name, and no template names a font. The "Role: Font" label format is the agent's call.

**Line-height:** a named scale in `settings.custom.lineHeight`, using Tailwind's names and values exactly, so a borrowed name means what it means everywhere else:
- `none` 1
- `tight` 1.25
- `snug` 1.375
- `normal` 1.5
- `relaxed` 1.625
- `loose` 2

Core turns `settings.custom.lineHeight.normal` into `--wp--custom--line-height--normal`. `theme.json` styles use them for body (`var:custom|line-height|normal`) and headings (`tight`), so Global Styles shows and edits those. The `var:custom|…` shorthand is a literal swap of `|` for `--`, so it must be written in kebab case: `line-height`, not `lineHeight`. `style.css` uses the same variables to set `none` on `xx-large` and up. `theme.json` has no line-height presets, so the block sidebar's line-height control stays a number field (checked in the living theme.json reference and in core 7.0.4 and 7.1.2).

**Shadows:** `primary` and `secondary`, named by role because most sites use one or two and their size differs per brand. The `primary` slug matches balloon-juice and Horizon West, whose values differ (`0 4px 16px rgba(0, 0, 0, 0.12)` and `0 10px 24px rgba(0, 0, 0, 0.05)`). Starter values are the agent's call. A block gets a default shadow through `styles.blocks.<block>.shadow` per client, not in the starter.

**Editor controls:** left on, as balloon-juice and Horizon West have them: custom font sizes, letter spacing, text transform, and writing mode. Sites switch them off as needed. Custom colours stay off, as all three themes have them.

**Radius sizes:** `default`, `half`, `quarter`, and `full`, following Horizon West's idea. `default` is the site's main radius, set once per client (starter value is the agent's call). `half` and `quarter` are computed from it, for example `calc(var(--wp--preset--border-radius--default) / 2)`, so a client changes one number and the fractions cannot drift the way balloon-juice's did (its `default` and `quarter` are both 6px). `full` is 9999px for pills, the name beof, Ollie, and Tailwind use. The builder first checks that core prints a `calc()` referencing another preset untouched, and falls back to hand-set values if not.

## CSS

**`style.css` holds only what `theme.json` cannot say,** loaded on the front end as the `mai` stylesheet with a `filemtime` version, and in the editor with `add_editor_style( 'style.css' )`.

- **Reset:** Josh Comeau's, every rule wrapped in `:where()`, at the top of `style.css`. Headings and paragraphs both get `text-wrap: pretty`.
- **Word wrapping:** `overflow-wrap: anywhere` on content areas only, not globally. balloon-juice puts it on post content and on comment author names. Mike is wary of it, so watch it on real content.
- **Footer stays at the bottom:** `.wp-site-blocks` as a flex column with a minimum height of `--mai-site-min-height`, the full viewport less the admin bar when it shows, and `main` growing to fill it.
- **Small base rules, from beof and balloon-juice:** `text-underline-offset`, `accent-color: primary`, cross-page view transitions with a reduced-motion guard, `.screen-reader-text`, `scroll-padding-top`, smooth scrolling only without reduced motion, `:target` scroll margin, list padding, and `scrollbar-gutter: stable`. Scrollbar colours are left to each client.
- **Focus:** one global `:focus-visible` outline. None of the three themes has one, so this is the agent's addition.
- **Line-height pairing:** the one rule setting `none` on the largest font sizes.

**No template width lives in CSS.** There are no `mai-theme-wide`, `mai-theme-narrow`, or `mai-theme-with-sidebar` classes. Each template sets its width in its own blocks (see "Templates").

**Per-block CSS goes in one file per block, in namespace folders:** `assets/css/blocks/core/navigation.css` is for `core/navigation`, and `assets/css/blocks/acme/grid-gallery.css` would be for `acme/grid-gallery`. Flat names like `acme-grid-gallery.css` cannot be read back reliably, because namespaces can contain hyphens. A loader of about 15 lines in the plumbing package lists the theme's folder and hands each file to core's `wp_enqueue_block_style()` with the handle `mai-<namespace>-<block>`, such as `mai-core-navigation`. Core prints a file only on pages where its block renders. Scanning the folder measured about 27 microseconds per page with 5 files. With on-demand block assets, core adds one small `render_block` check per file (read in `script-loader.php`, WordPress 7.1.2). A client site can still put CSS strings in `theme.json` when that is quicker.

The starter's own block CSS is expected to be small: the navigation overlay and its open state, the card image radius in Post Template, and the sidebar Search block.

## Block styles

**Block styles are JSON files in `styles/blocks/<block>/`, with no PHP.** Core reads any file in `styles/`, including subfolders, that has a `blockTypes` key as a block style (read in core's theme JSON resolver). Ollie uses this, for example `styles/blocks/button/button-brand-1.json`. A style that needs real CSS, like an arrow drawn with `::after`, keeps its JSON file and puts the extra rules in its block's CSS file.

**Two rules for these files, from core's code:**
- **Give every file an explicit `slug`.** Without one, core builds the slug from the title, so "Alt Heading" would become `alt-heading` (`block-supports/block-style-variations.php`).
- **Every file needs at least one style property.** Core skips a file whose `styles` is empty, both when registering it and when merging it in.

**The starter ships one: `altheading`, labelled "Alt Heading", on Heading and Paragraph.** It is nearly plain, for each client to style. Agent's call: its one property is `fontFamily: var:preset|font-family|heading`, which is invisible in the starter (both families are Figtree) and makes an Alt Heading paragraph use the heading font on client sites. The slug matches three v2 client sites, where it is on Heading only: agipackagepumpsystems (`~/Herd/agipackagedpumpsystems`), hydroplex, and bistro90 (`~/Herd/pizzeria90`). So `is-style-altheading` is a class people already know. Adding Paragraph is new. It breaks the house rule of hyphens in slugs on purpose, and `AGENTS.md` should say so. "Subheading" and "eyebrow" were rejected as names that promise a job. "Alt Heading" is just "the other heading style", which suits sites that need none, one, or a different look each time.

## PHP

**The starter's plumbing is a Composer package, decided 2026-10-20.** Named `maithemewp/mai-theme-core` by Mike: Mai Theme's own core, the way Mai Engine was v2's. It holds small files and nothing a client customises:
- the `style.css` enqueue and `add_editor_style()`, since they read the active theme's own files
- the block CSS loader
- the default-preset filter
- stripping core's legacy preset classes from its inline block CSS (see "theme.json")
- the dependency installer config for Mai Content Areas and Mai Columns, requiring `afragen/wp-dependency-installer` itself, and the notice label filter (see "Dependencies")
- the `mai/current-year` binding
- the `sidebar` template part area
- skipping `front-page.html` when the site shows its latest posts on the front page, so a fresh install shows posts rather than an empty page
- emoji removal, as all three themes do
- the login page (see below)
- Gravity Forms colours from the `theme.json` palette, beof's typed version, loaded only when Gravity Forms is active
- a 16:9 shape for video embeds in old classic posts, from balloon-juice's `inc/embed-shape.php`
- stripping empty `<p></p>` from rendered content, from balloon-juice's `strip_empty_paragraphs`, at render only and never in stored content
- an Appearance → Patterns link to the synced patterns list, from balloon-juice's `add_patterns_link`

**How it loads:** Composer's `autoload.files`, no classes needed, namespace `Mai\Theme\Core`, matching `Mai\Slots` and `Mai\ContentAreas`, with `declare( strict_types=1 );` in every file. It does not need mai-package-loader, because only one theme is ever active. Every function is named and hooked, as in beof, so a site can `remove_action()` one or filter its result instead of editing it.

**The login page is ported from balloon-juice's `CustomLogin`** (`balloon-juice/inc/login.php`, a cleaner copy of Horizon West's `inc/login.php`) as named, hooked functions. Mai Engine's version depends on Kirki and is not reusable.
- **The look:** a `base-2` page background. The site logo centred above the form, at most 100px tall, or the Site Title in the heading font. The form in a `base` card with the `default` radius, the `primary` shadow, and a `base-3` border. The body font in fields with a `primary` focus ring, the theme's own button style on Log In, and small `contrast-2` links under the form.
- **Styles and fonts:** it prints the global stylesheet, so `theme.json` tokens and button styles apply, and prints fonts with core's `wp_print_font_faces()`. `CustomLogin` enqueues the font files as stylesheets instead, which is unverified and probably redundant.
- **Customising, in three layers, with no class to extend:** the `theme.json` tokens. An optional `assets/css/login.css` in the active theme, loaded after the package's styles, with the variables `--mai-login-background`, `--mai-login-card-background`, and `--mai-login-logo-height`. And the named hooks, which a theme can `remove_action()`.
- **Names:** the stylesheet handles are `mai-login-global`, `mai-login`, and `mai-login-theme`, and hooks start `mai_login_`. Agent's call: the package adds no login filters yet. The `mai_login_` prefix is for any hook added later. The login functions themselves are named functions in `Mai\Theme\Core`, which a theme can `remove_action()`.

**While the starter is being built,** the package is a path repository at `@dev` from `~/LocalPackages/mai-theme-core`, the way mai-content-areas uses the engine today. Composer symlinks a path repository into `vendor/`, which cannot ship, so the switch to the GitHub repository happens with the first release. No tags until the plumbing settles. After that each release needs Mike's yes, and the theme commits `vendor/` like the fleet's plugins.

**Why a package:**
- **Starter fixes reach old client copies** with `composer update` and a deploy, instead of hand-merging files. Horizon West's `TODO.md` shows the drift this prevents: its `Term_Image` class is an old copy of balloon-juice's and never got a fix.
- **Every client copy's plumbing version is visible** in its `composer.lock`.
- **Nobody edits it by accident,** since it sits under `vendor/`.
- **Doing it later would mean migrating every client copy** from a folder to the package by hand.
- **It stays far from Mai Builder:** no helpers and no config API, just hooks that run when the files load.

**The theme's own PHP:**
- **`functions.php` uses the namespace `Mai\Theme`,** the way Ollie uses `Ollie`. It only loads Composer's autoloader, then `inc/*.php`. The package's `Mai\Theme\Core` sits apart from it, so a function in one cannot clash with a function in the other.
- **`inc/` is the site's own PHP,** empty in the starter, as `inc/` means in the house plugin convention. Code there uses the client's own namespace. Client features still go in the client's own plugin, as beof's blocks live in `beof-plugin`.
- **Renaming a client copy** changes the folder and the `style.css` header (see "How a client site starts"). The package keeps `Mai\Theme\Core` and its `mai` handles everywhere and never reads the theme's slug, so it never needs renaming.

**The `<head>` after the filter:** beof's live head prints none of core's gradient, duotone, or shadow variables, but core's common block CSS still carries the legacy gradient classes (see "theme.json"). The rest is ordinary: global styles, local font faces, the feed link, canonical, the skip link CSS, per-block CSS, two oEmbed discovery links, and REST API links. Speculation rules print in the footer. The starter leaves the oEmbed and REST links in.

## Conventions

**House block theme conventions move into a `mai-theme-scaffold` skill in `~/.agents/skills`,** naming `mai-theme` as the reference theme, the way `mai-plugin-scaffold` names `mai-auth` for plugins. One copy of the rules then updates everywhere, where a conventions file inside the theme would freeze in every client copy.

**Decided 2026-10-20: writing the skill is the build's first step,** distilled from this document and walked with Mike as its own review before the theme points at it.

**Keeping it up to date, agent's call:** `mai-theme`'s `AGENTS.md` says that any change to a house convention in this repo updates the skill in the same session. The skill says, as `mai-plugin-scaffold` does about `mai-auth`, that when it and `mai-theme` disagree, the agent reads the theme and tells Mike.

**Two house rules from Mike's review, in both the skill and the theme's `AGENTS.md`:**
- **The starter never relies on Mai Slots rules for base content.** No block in the starter's markup carries a "Show when" rule (`maiSlotsRules`). Where posts and pages need different blocks, they get different parts or templates, as `entry-header` and `page-header` do. Rules are a feature for client builds and later work.
- **A value is set once, in `theme.json`.** A block carries a style setting only when it really differs (see "theme.json").

**Each theme's `AGENTS.md` keeps only that site's rules.** The starter's `AGENTS.md` points to the skill at the top and has an empty "This site" section. A site rule that overrides a house rule says so by name. A site rule that proves good everywhere moves up into the skill.

**balloon-juice's `CONVENTIONS.md` is out of date** in places: it says "no resets", keeps line-height out of `theme.json`, and lists radius names no theme uses. A note in balloon-juice's `TODO.md` says to point it at the skill once the skill exists. Both other themes' `TODO.md` files also note converting their raw preset variables to the shorthand. balloon-juice and Horizon West had their block settings that repeat `theme.json` removed on 2026-10-22, with matching before-and-after measurements (`~/tmp/theme-json-repeats/summary.md`), and both were pushed on 2026-10-23 (balloon-juice `22476bd` on `develop`, Horizon West `29d375d`).

## Later: a pattern library

Mike would like a pattern library that inherits each site's styles automatically, likely when and if this becomes a premium theme. Sources would include Ollie (GPL), Rockbase (Mike's friend Rafal has offered patterns, and the licence has not been seen), and others, rebuilt in Mai's own tokens.

- **Patterns only reference presets:** colour roles, spacing `10` to `80`, the font sizes, `body` and `heading`, and the two shadows. No raw values. The token names in this document are therefore a contract, and should not change lightly.
- **Section styles** let one pattern work on light and dark bands. Parked until this phase.
